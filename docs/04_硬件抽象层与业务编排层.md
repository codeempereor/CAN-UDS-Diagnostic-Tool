# 04 — 硬件抽象层与业务编排层

## 4.1 CanAdapterBase 抽象基类

**文件：** `src/hal/can_adapter_base.h` + `.cpp`

### 这是适配器模式的核心

```cpp
class CanAdapterBase {
public:
    // 纯虚函数，子类必须实现
    virtual bool open(const std::string& interface, uint32_t bitrate) = 0;
    virtual void close() = 0;
    virtual bool sendFrame(const CanFrame& frame) = 0;
    virtual bool isOpen() const = 0;
    virtual std::string adapterName() const = 0;

    // 回调设置（普通函数，子类继承）
    void setReceiveCallback(ReceiveCallback callback);
    void setErrorCallback(ErrorCallback callback);
    void setStateChangedCallback(StateChangedCallback callback);

protected:
    // 通知函数（子类调用，基类实现）
    void notifyReceived(const CanFrame& frame);
    void notifyError(const std::string& error);
    void setState(CanAdapterState state);
};
```

### 设计要点

- `= 0` 纯虚函数 → 抽象类，不能实例化，只能当指针/引用用
- 子类只管硬件相关的open/close/sendFrame
- 通知逻辑（回调调用）在基类实现，子类不用重复写
- 这是**模板方法模式**：基类定义算法骨架（通知流程），子类实现具体步骤

### notifyReceived

```cpp
void CanAdapterBase::notifyReceived(const CanFrame& frame) {
    if (m_receiveCallback) {
        m_receiveCallback(frame);  // 有回调就调用，没有就静默
    }
}
```

### setState 状态变更通知

```cpp
void CanAdapterBase::setState(CanAdapterState state) {
    if (m_state != state) {  // 状态真的变了才通知，避免重复
        m_state = state;
        if (m_stateCallback) m_stateCallback(state);
    }
}
```
- 先判断是否真的变化，避免重复通知
- 这是一个小优化，但很重要

## 4.2 VirtualCanAdapter 虚拟适配器

**文件：** `src/hal/virtual_can_adapter.h` + `.cpp`

### 设计目标

没有真实硬件时也能开发测试。模拟一个ECU，收到诊断请求自动回复。

### 核心成员

```cpp
std::atomic<bool> m_running;     // 原子变量，线程安全的运行标志
std::thread m_receiveThread;     // 接收线程
std::mutex m_mutex;
bool m_simulateEcu;              // 是否模拟ECU响应
uint8_t m_currentSession;        // 模拟ECU的当前会话状态
```

### 为什么用std::atomic？

```cpp
std::atomic<bool> m_running;
```
- `m_running` 会被两个线程访问：接收线程读，主线程写
- 普通bool在多线程下可能有可见性问题（一个线程改了，另一个线程看不到）
- `std::atomic<bool>` 保证原子性和可见性

### open 启动接收线程

```cpp
bool VirtualCanAdapter::open(const std::string& interface, uint32_t bitrate) {
    if (m_running) return false;

    m_running = true;
    setState(CanAdapterState::Open);

    // 启动接收线程，lambda作为线程函数
    m_receiveThread = std::thread([this]() {
        receiveThread();
    });

    return true;
}
```

### receiveThread 接收线程主循环

```cpp
void VirtualCanAdapter::receiveThread() {
    uint32_t counter = 0;
    while (m_running) {
        // 每100ms发一帧模拟报文
        std::this_thread::sleep_for(std::chrono::milliseconds(100));

        CanFrame frame;
        frame.id = 0x100 + (counter % 4);  // 0x100~0x103循环
        frame.dlc = 8;
        frame.data.resize(8);
        for (int i = 0; i < 8; i++) {
            frame.data[i] = static_cast<uint8_t>((counter + i) & 0xFF);
        }
        frame.timestamp_us = CanFrame::currentTimestampUs();

        notifyReceived(frame);  // 通知上层"收到"一帧
        counter++;
    }
}
```

### 知识点

- `std::this_thread::sleep_for` — 当前线程睡眠一段时间
- `std::chrono::milliseconds(100)` — 100毫秒
- 虚拟适配器就是定时构造假帧，通过notifyReceived发出去
- 上层以为是真实硬件收到的，完全无感知

### sendFrame 发送帧（模拟ECU响应）

```cpp
bool VirtualCanAdapter::sendFrame(const CanFrame& frame) {
    if (!m_running) return false;

    // 自发自收：把发送的帧也回显给上层
    notifyReceived(frame);

    // 如果开启了ECU模拟，且是诊断请求ID，自动回复
    if (m_simulateEcu && frame.id == m_ecuRxId) {
        simulateEcuResponse(frame);
    }
    return true;
}
```

### simulateEcuResponse 模拟ECU响应（核心）

```cpp
void VirtualCanAdapter::simulateEcuResponse(const CanFrame& request) {
    if (request.dlc < 2) return;

    uint8_t serviceId = request.data[1];  // data[0]是ISO-TP PCI，data[1]才是UDS服务ID
    CanFrame response;
    response.id = m_ecuTxId;
    response.dlc = 8;
    response.data.resize(8, 0);

    switch (serviceId) {
    case 0x10: {  // 会话控制
        uint8_t session = request.data[2];
        m_currentSession = session;
        response.data[0] = 0x06;   // ISO-TP单帧，长度6
        response.data[1] = 0x50;    // 肯定响应 = 0x10+0x40
        response.data[2] = session; // 回显会话类型
        break;
    }
    case 0x22: {  // 读DID
        uint16_t did = (request.data[2] << 8) | request.data[3];
        auto didData = getSimulatedDidData(did);
        // 构造肯定响应 0x62 + DID + 数据
        response.data[1] = 0x62;  // 肯定响应
        response.data[2] = request.data[2];
        response.data[3] = request.data[3];
        size_t copyLen = std::min<size_t>(4, didData.size());
        memcpy(response.data.data() + 4, didData.data(), copyLen);
        response.data[0] = static_cast<uint8_t>(3 + copyLen);  // PCI长度
        response.dlc = static_cast<uint8_t>(4 + copyLen);
        break;
    }
    // ... 其他服务
    }

    response.timestamp_us = CanFrame::currentTimestampUs();
    notifyReceived(response);  // 把"ECU的响应"发出去
}
```

### 关键理解

- 虚拟适配器同时扮演"总线"和"ECU"两个角色
- 收到诊断请求后，构造一个符合UDS规范的响应帧
- 通过notifyReceived发出去，上层以为是真ECU回复的
- 这样整个链路（发请求→ISO-TP分片→ECU响应→ISO-TP重组→UDS解析）都能测试

## 4.3 为什么需要业务层

核心协议栈是纯C++的，用std::function回调。
但Qt的世界里，大家用信号槽，而且要跨线程。
业务层（Manager们）就是**把核心层包装成Qt友好的接口**：
- 用QObject + 信号槽代替std::function
- 管理线程（接收线程、定时器）
- 管理生命周期（创建、销毁、连接）

## 4.4 CanManager CAN管理器

**文件：** `src/business/can_manager.h` + `.cpp`

### 核心职责

1. 持有适配器对象
2. 管理接收线程
3. 把适配器的回调转换成Qt信号
4. 统计、过滤

### start 启动

```cpp
bool CanManager::start(AdapterType type, const QString& interface, uint32_t bitrate) {
    // 1. 根据类型创建适配器（工厂思想）
    if (type == Virtual) {
        m_adapter = std::make_unique<VirtualCanAdapter>();
    } else {
        m_adapter = std::make_unique<SocketCanAdapter>();
    }

    // 2. 设置回调（适配器收到帧 → 调用我们的槽）
    m_adapter->setReceiveCallback([this](const CanFrame& frame) {
        onAdapterReceived(frame);
    });

    // 3. 打开适配器
    if (!m_adapter->open(interface.toStdString(), bitrate)) {
        return false;
    }

    // 4. 启动统计定时器，每秒发一次统计信号
    m_statsTimer->start(1000);
    return true;
}
```

### onAdapterReceived 接收回调（可能在子线程调用）

```cpp
void CanManager::onAdapterReceived(const CanFrame& frame) {
    m_stats.update(frame);  // 更新统计

    if (m_filter.pass(frame)) {
        // 过滤通过，放入缓冲（加锁，因为可能跨线程）
        QMutexLocker locker(&m_bufferMutex);
        m_frameBuffer.append(frame);
        // 不直接发信号，因为可能在非GUI线程
    }
}
```

### 为什么不直接发信号？

- 适配器的接收回调在接收线程调用
- Qt信号如果跨线程，会排队到接收者的线程
- 但如果一帧发一次信号，上千帧每秒，信号队列会爆
- 所以先缓冲，GUI线程用定时器批量取

### processFrames 批量处理（GUI线程定时器调用）

```cpp
void CanManager::processFrames() {
    QList<CanFrame> frames;
    {
        QMutexLocker locker(&m_bufferMutex);
        frames.swap(m_frameBuffer);  // 用swap高效取出，O(1)
    }

    for (const auto& frame : frames) {
        emit frameReceived(frame);  // 逐帧发信号给GUI
    }
}
```

### 知识点

- `QMutexLocker` — Qt的RAII锁，类似std::lock_guard
- `frames.swap(m_frameBuffer)` — 交换两个容器，O(1)复杂度，比拷贝高效
- 先加锁取出所有数据，解锁后再发信号，减少锁持有时间

## 4.5 DbcManager DBC管理器

**文件：** `src/business/dbc_manager.h` + `.cpp`

### 职责

### parseFrameSignals 解析一帧的所有信号

```cpp
std::map<QString, double> DbcManager::parseFrameSignals(const CanFrame& frame) const {
    std::map<QString, double> result;

    const DbcMessage* msg = m_parser->getMessage(frame.id);
    if (!msg) return result;  // 这个ID没有DBC定义

    // 调用核心层的getAllValues，返回 std::map<string, double>
    auto values = msg->getAllValues(frame.data.data(), frame.dlc);

    // 转成QString的map（Qt风格）
    for (const auto& pair : values) {
        result[QString::fromStdString(pair.first)] = pair.second;
    }
    return result;
}
```

### 设计要点

- 业务层持有 `DbcParser` 核心对象
- 对外提供Qt风格的接口（QString、信号）
- 内部调用核心层的纯C++接口
- 这就是**外观模式（Facade）**：把复杂的子系统封装成简单接口

## 4.6 DiagManager 诊断管理器

**文件：** `src/business/diag_manager.h` + `.cpp`

### 职责

把UdsClient包装成Qt友好的接口，管理诊断会话。

### 连接CAN管理器

```cpp
void DiagManager::setCanManager(CanManager* canManager) {
    m_canManager = canManager;

    // CAN收到帧 → 传给UDS客户端
    connect(m_canManager, &CanManager::frameReceived,
            this, &DiagManager::onFrameReceived);

    // UDS要发帧 → 调用CAN管理器发送
    m_udsClient.setSendFrameCallback([this](const CanFrame& frame) {
        if (m_canManager) m_canManager->sendFrame(frame);
    });

    // UDS收到响应 → 发Qt信号
    m_udsClient.setResponseCallback([this](const UdsResponse& resp) {
        emit responseReceived(resp);
    });
}
```

### 数据流向

```
CAN硬件 → CanManager(frameReceived信号) → DiagManager(onFrameReceived)
    → UdsClient.handleReceivedFrame → IsoTpClient重组 → UdsClient解析
    → response回调 → DiagManager(responseReceived信号) → GUI
```

这就是典型的**观察者模式链式调用**，每层只关心自己的上下家。

### onFrameReceived 过滤诊断帧

```cpp
void DiagManager::onFrameReceived(const CanFrame& frame) {
    // 只把诊断ID的帧传给UDS客户端
    if (frame.id == m_udsClient.rxId()) {
        m_udsClient.handleReceivedFrame(frame);
    }
}
```
- 不是所有CAN帧都是诊断帧，只把RX ID匹配的传给UDS
- 避免UDS客户端处理无关帧

## 4.7 SignalManager 信号管理器

**文件：** `src/business/signal_manager.h` + `.cpp`

### 职责

缓存信号的历史值，为波形面板提供数据源。

### SignalData 结构

```cpp
struct SignalData {
    QString name;
    uint32_t canId = 0;
    std::deque<double> values;      // 历史值（双端队列，头部删尾部加）
    std::deque<uint64_t> timestamps; // 时间戳
    double minValue = 0;
    double maxValue = 0;
    bool visible = true;
    QColor color;
    static constexpr size_t MAX_POINTS = 10000;  // 最多保留10000个点
};
```

### 为什么用std::deque？

- 波形数据需要尾部加新点，头部删旧点
- `std::deque` 双端队列，头尾操作都是O(1)
- `std::vector` 头部删除是O(n)，效率低

### onSignalValueReceived 接收信号值

```cpp
void SignalManager::onSignalValueReceived(const QString& name, double value, uint64_t timestamp) {
    auto it = m_signals.find(name);
    if (it == m_signals.end()) return;  // 信号不存在

    SignalData& sig = it.value();
    sig.values.push_back(value);
    sig.timestamps.push_back(timestamp);

    // 限制最大点数，超过就删最旧的
    while (sig.values.size() > MAX_POINTS) {
        sig.values.pop_front();
        sig.timestamps.pop_front();
    }

    // 更新最大最小值
    if (value < sig.minValue) sig.minValue = value;
    if (value > sig.maxValue) sig.maxValue = value;
}
```

### signalData 取信号数据（const函数）

```cpp
const SignalData* SignalManager::signalData(const QString& name) const {
    auto it = m_signals.constFind(name);
    if (it == m_signals.constEnd()) return nullptr;
    return &it.value();
}
```
- `constFind` — QMap的const查找，不修改容器
- 返回const指针，调用者不能修改数据

## v1.1 更新补充：DiagManager 保活与超时、SignalManager 单位

### 一、DiagManager 超时检查定时器

#### 为什么业务层需要定时器？

核心协议栈的 `IsoTpClient::checkTimeout()` 和 `UdsClient::checkTimeout()` 需要**外部定期调用**才能检测超时。核心层是纯C++，没有Qt的事件循环，所以由业务层的 `DiagManager` 用 `QTimer` 驱动。

#### 构造函数中启动定时器

```cpp
DiagManager::DiagManager(QObject* parent)
    : m_timeoutTimer(new QTimer(this))
    , m_testerPresentTimer(new QTimer(this))
{
    // 每100ms检查一次ISO-TP和UDS超时
    connect(m_timeoutTimer, &QTimer::timeout, this, &DiagManager::onCheckTimeout);
    m_timeoutTimer->start(100);

    // TesterPresent保活定时器，默认3秒
    connect(m_testerPresentTimer, &QTimer::timeout, this, &DiagManager::onTesterPresentTimer);
    m_testerPresentTimer->setInterval(3000);
}
```

#### onCheckTimeout 转发到核心层

```cpp
void DiagManager::onCheckTimeout() {
    m_udsClient->checkTimeout();  // 内部会调用IsoTpClient::checkTimeout()
}
```

**设计要点：**
- 100ms检查一次，对1秒超时来说精度足够（误差<10%）
- 定时器在GUI线程运行，不会阻塞接收线程
- 超时后核心层通过 `ErrorCallback` / `UdsErrorCallback` 通知，DiagManager用 `QueuedConnection` 跨线程转发为Qt信号

#### 错误信号

```cpp
signals:
    void timeoutOccurred(int errorType);       // ISO-TP层错误
    void udsErrorOccurred(int errorType, uint8_t serviceId);  // UDS层错误
```

### 二、DiagManager TesterPresent 自动保活

#### 为什么需要保活？

UDS诊断会话（如扩展会话0x03、编程会话0x02）有**会话超时**——如果ECU在一段时间内（通常5秒）没有收到任何诊断请求，会自动回退到默认会话，之前解锁的安全访问也会失效。

`TesterPresent`（0x3E服务）就是专门用来"保活"的——告诉ECU"我还在，别超时"。

#### 智能保活逻辑

```cpp
void DiagManager::onTesterPresentTimer() {
    // 只有在非默认会话且没有pending请求时才发送保活
    if (m_udsClient->currentSession() != UdsSessionType::DefaultSession
        && !m_udsClient->hasPendingRequest()) {
        m_udsClient->testerPresent(true);  // suppressPositiveResponse=true
    }
}
```

**三个关键判断：**
1. **非默认会话** — 默认会话不需要保活（默认会话永不超时）
2. **无pending请求** — 如果正在等其他请求的响应，不需要额外发保活（那个请求本身就在保活）
3. **suppressPositiveResponse=true** — 子函数字节最高位置1，ECU收到后不回复肯定响应，避免占用总线

#### 控制接口

```cpp
void setTesterPresentEnabled(bool enabled);   // 启用/禁用保活
bool isTesterPresentEnabled() const;            // 查询状态
void setTesterPresentIntervalMs(int intervalMs); // 调整周期（默认3000ms）
```

**启用时启动定时器，禁用时停止定时器：**
```cpp
void DiagManager::setTesterPresentEnabled(bool enabled) {
    m_testerPresentEnabled = enabled;
    if (enabled) m_testerPresentTimer->start();
    else m_testerPresentTimer->stop();
}
```

### 三、SignalManager 新增 unit 字段

#### 为什么需要unit？

原始 `SignalData` 只有数值，没有单位。信号数值面板需要显示"rpm"、"degC"、"bar"等单位，所以需要在SignalData中存储单位。

#### SignalData 新增字段

```cpp
struct SignalData {
    QString name;
    uint32_t canId = 0;
    QString unit;           // 新增：信号单位（如"rpm"、"degC"）
    std::deque<double> values;
    std::deque<uint64_t> timestamps;
    // ...
};
```

#### setSignalUnit 接口

```cpp
void SignalManager::setSignalUnit(const QString& name, const QString& unit) {
    if (m_signals.contains(name)) {
        m_signals[name].unit = unit;
    }
}
```

#### MainWindow 中DBC加载时设置单位

```cpp
void MainWindow::onDbcLoaded(bool success) {
    auto messages = m_dbcManager->allMessages();
    for (const auto& pair : messages) {
        for (const auto& sig : pair.second.signalList) {
            QString sigName = QString::fromStdString(sig.name);
            m_signalManager->addSignal(sigName, pair.first);
            m_signalManager->setSignalUnit(sigName, QString::fromStdString(sig.unit));  // 设置单位
        }
    }
}
```

**设计要点：**
- 单位是DBC信号的元数据，在DBC加载时一次性设置
- 运行中信号值变化时，单位不变，不需要每次更新
- 信号数值面板从 `SignalData::unit` 读取并显示在"单位"列

### 知识点

- `std::fixed << std::setprecision(6)` — 固定6位小数输出
- `std::hex` — 十六进制输出
- `std::setw(2) << std::setfill('0')` — 宽度2，不足补0
- 需要 `#include <iomanip>` 才能用这些格式化操作符
