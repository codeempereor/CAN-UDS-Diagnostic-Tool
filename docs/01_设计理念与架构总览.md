# 01 — 设计理念与架构总览

## 1.1 项目要解决什么问题

汽车电子开发中，工程师需要：
1. **监听CAN总线** — 实时查看总线上跑了哪些报文
2. **解析DBC** — 把原始字节翻译成物理值（转速、温度、车速）
3. **UDS诊断** — 给ECU发诊断指令，读数据、写数据、刷程序
4. **日志回放** — 录制现场数据，回来慢放分析问题

市面上的工具（CANoe、PCAN-View）要么贵，要么闭源，要么不好二次开发。
本项目做一个**开源、分层、可扩展**的CAN总线分析工具。

## 1.2 四大核心设计理念

### 理念一：协议栈与GUI彻底解耦

**为什么？**
- 核心协议（CAN/DBC/ISO-TP/UDS）是纯算法，不应该依赖Qt
- 核心代码可以在嵌入式设备上直接用
- 可以单独写单元测试，不需要启动GUI
- 以后想换GUI框架（比如从Qt换成ImGui），核心不用动

**怎么做的？**
```
src/core/    ← 纯C++17，零Qt依赖，可独立编译测试
src/hal/     ← 硬件抽象，也不依赖Qt
src/business/← 开始用Qt的Core模块（信号槽、线程）
src/gui/     ← Qt Widgets，纯界面
```

### 理念二：面向接口编程，不面向实现

**为什么？**
- 硬件适配器有很多种：SocketCAN、PCAN、ZLG、虚拟适配器
- 如果业务层直接依赖具体硬件，换硬件就要改业务代码
- 用抽象基类定义接口，业务层只认接口，不认具体实现

**怎么做的？**
```cpp
class CanAdapterBase {  // 抽象基类
    virtual bool open(...) = 0;
    virtual void close() = 0;
    virtual bool sendFrame(...) = 0;
};
class VirtualCanAdapter : public CanAdapterBase { ... };
class SocketCanAdapter : public CanAdapterBase { ... };
```
业务层持有 `CanAdapterBase*` 指针，运行时才决定用哪个实现。
这就是**多态**，也是**策略模式**的基础。

### 理念三：观察者模式贯穿全项目

**为什么？**
- 底层收到数据要通知上层，但底层不应该知道上层是谁
- 一个数据可能要同时通知多个模块（显示、记录、解析）
- 用回调/信号槽，底层只管"我收到了，谁关心谁来拿"

**怎么做的？**
- 核心层用 `std::function` 回调（C++标准，不依赖Qt）
- Qt层用信号槽（Signal/Slot，Qt的观察者实现）

数据流向：
```
硬件 → CanAdapterBase(回调通知) → CanManager(信号) → 各面板(槽函数)
```

### 理念四：线程隔离，GUI绝不阻塞

**为什么？**
- CAN总线数据率很高（500kbps下每秒上千帧）
- 如果在GUI线程里收数据、解析数据，界面会卡
- Qt规定GUI控件只能在主线程操作

**怎么做的？**
```
接收线程：硬件收帧 → 放入队列
主线程：定时器批量取队列 → 更新界面
```
用 `QTimer` 每50ms刷新一次界面，而不是来一帧刷一帧。

## 1.3 四层架构详解

```
┌─────────────────────────────────────────────┐
│  GUI视图层 (Qt Widgets)                      │
│  主窗口 + 5个面板，纯展示和交互               │
├─────────────────────────────────────────────┤
│  业务编排层 (Qt Core)                        │
│  Manager们：把核心层包装成Qt友好的接口        │
│  CanManager / DbcManager / DiagManager ...   │
├─────────────────────────────────────────────┤
│  核心协议栈 (纯C++17)                        │
│  CAN帧 / DBC解析 / ISO-TP / UDS              │
│  零Qt依赖，可独立移植                        │
├─────────────────────────────────────────────┤
│  硬件抽象层 (HAL)                            │
│  CanAdapterBase 抽象基类                     │
│  虚拟适配器 / SocketCAN / (未来加PCAN等)     │
└─────────────────────────────────────────────┘
```

**层与层之间的依赖规则：**
- 上层可以依赖下层，下层绝对不能依赖上层
- 每层只通过接口与下层通信
- 同层模块之间尽量低耦合

## 1.4 用到的设计模式总结

| 设计模式 | 用在哪里 | 解决什么问题 |
|---------|---------|------------|
| **观察者模式** | 回调函数、Qt信号槽 | 底层数据通知上层，解耦 |
| **策略模式** | 硬件适配器可替换、过滤模式切换 | 运行时切换算法/实现 |
| **状态模式** | ISO-TP发送/接收状态机 | 复杂状态流转，避免if-else地狱 |
| **适配器模式** | CanAdapterBase统一接口 | 不同硬件统一操作方式 |
| **模板方法** | 适配器基类定义notify流程 | 子类只管收数据，通知逻辑复用 |
| **外观模式** | Manager封装核心层 | 把复杂子系统包装成简单接口 |
| **中介者模式** | MainWindow连接各组件 | 组件间不直接依赖，通过中介协调 |
| **RAII** | lock_guard、文件句柄 | 资源自动释放，不会忘记解锁/关闭 |

### 三、嵌入式移植可行性

核心协议栈（CAN/DBC/ISO-TP/UDS）纯C++17实现，零Qt依赖，零平台依赖，可直接移植到嵌入式平台：

- **STM32F407**：Cortex-M4 168MHz，192KB RAM，2路bxCAN，FreeRTOS，约75h工作量
- **TC275**：TriCore三核200MHz，550KB RAM，4路MultiCAN+（支持CAN FD），HSM硬件安全，约100h工作量

移植路线：STM32裸机 → STM32+FreeRTOS → TC275+FreeRTOS → TC275+AUTOSAR
