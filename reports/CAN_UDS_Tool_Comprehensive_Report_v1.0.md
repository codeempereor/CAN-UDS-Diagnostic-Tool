## 一、项目概述

从0到1自研的车载CAN总线分析与UDS诊断工具，对标CANoe基础功能。核心协议栈纯C++零Qt依赖，四层架构可移植到嵌入式平台。当前版本已完成GUI可视化、协议栈、工程化三大体系，支持虚拟适配器无硬件开发。

## 三、已实现功能

### 3.1 核心协议栈（纯C++，零Qt依赖）

#### CAN基础模块
- **CAN帧结构**：标准帧/扩展帧，ID/DLC/data(8字节)/时间戳
- **ID过滤器**：白名单/黑名单/掩码过滤，支持多ID组合
- **总线统计**：帧计数/字节计数/负载率/ID分布/错误帧/远程帧
- **4项单元测试**通过

#### DBC解析模块
- **BO_报文解析**：报文ID/名称/DLC/发送节点
- **SG_信号解析**：信号名/起始位/长度/大小端/有符号无符号/系数/偏移/最小最大/单位
- **VAL_枚举值表**：信号值到描述的映射
- **位提取算法**：Intel小端 + Motorola大端，修复大端跨字节越界bug
- **物理值转换**：原始值 → 系数×原始值+偏移 → 物理值
- **7项边界测试**：8位/4位/16位/12位/24位/全0/全1

#### ISO-TP多帧传输（ISO 15765-2）
- **四种帧**：单帧(SF)/首帧(FF)/连续帧(CF)/流控帧(FC)
- **状态机**：发送方状态机 + 接收方状态机
- **流控参数**：块大小(BS)/最小间隔(STmin)
- **超时检测**：流控超时/连续帧超时/序列号错误/接收方溢出（4种）
- **死锁修复**：回调重入死锁（mutex→recursive_mutex）
- **3项单元测试**通过

#### UDS诊断客户端（ISO 14229-1）
- **6种诊断服务**：
  - 0x10 诊断会话控制（默认会话/扩展会话/编程会话）
  - 0x22 读数据标识符（ReadDataByIdentifier）
  - 0x2E 写数据标识符（WriteDataByIdentifier）
  - 0x31 例程控制（RoutineControl）
  - 0x11 ECU复位（ECUReset）
  - 0x3E TesterPresent保活
- **0x27 安全访问**：4状态机（Idle→WaitingForSeed→WaitingForKey→Unlocked），密钥计算通过std::function策略模式注入
- **请求队列**：半双工保护，拒绝并发请求，响应serviceId匹配
- **3秒超时机制**：请求超时自动失败
- **4项单元测试**通过

## 四、架构设计

### 4.1 四层架构

```
┌─────────────────────────────────────────────────┐
│ GUI视图层 (Qt Widgets) — 8个面板 + MainWindow   │
│  信号槽连接，中介者模式，QPainter自绘波形        │
├─────────────────────────────────────────────────┤
│ 业务编排层 (Qt Core) — 5个Manager                │
│  双缓冲批量处理，观察者链，请求队列，超时检查     │
├─────────────────────────────────────────────────┤
│ 核心协议栈 (纯C++17, 零Qt依赖)                   │
│  CAN/DBC/ISO-TP/UDS — 可独立编译/测试/移植      │
├─────────────────────────────────────────────────┤
│ 硬件抽象层 (HAL) — CanAdapterBase + 实现         │
│  虚拟适配器 / SocketCAN / 可扩展PCAN/ZLG         │
└─────────────────────────────────────────────────┘
```

### 4.2 设计模式清单（8种）

| 模式 | 应用位置 |
|------|---------|
| **观察者** | Manager回调 + Qt信号槽，帧接收→解析→显示链式通知 |
| **策略** | UDS安全访问密钥计算（std::function注入），硬件适配器可替换 |
| **状态** | ISO-TP发送/接收状态机，UDS请求状态机，安全访问4状态机 |
| **适配器** | CanAdapterBase抽象接口，不同硬件适配器统一接口 |
| **模板方法** | 适配器基类定义流程，子类实现硬件相关细节 |
| **外观** | Manager封装底层协议栈复杂度，对外提供简化接口 |
| **中介者** | MainWindow统一连接各面板，面板间不直接依赖 |
| **RAII** | 锁/文件句柄/资源自动管理 |

### 4.3 关键设计决策

1. **核心层零Qt依赖**：可移植到STM32+FreeRTOS，可独立单元测试
2. **单向依赖**：上层依赖下层，下层不感知上层
3. **面向抽象编程**：硬件/协议/模块均基于接口，可插拔替换
4. **多线程分离**：接收线程与GUI线程分离，双缓冲+定时器批量刷新避免卡顿

### 6.2 阶段1：USB-CAN适配器（入门级，成本低）

#### 推荐硬件

| 设备 | 接口 | 通道 | 波特率 | 价格区间 | 说明 |
|------|------|------|--------|---------|------|
| **创芯科技 CANalyst-II** | USB | 1路 | 5K-1M | ¥150-300 | 国产入门，有DLL，资料多 |
| **广成科技 USBCAN-II** | USB | 2路 | 5K-1M | ¥300-600 | 国产，2路同时收发，DLL完善 |
| **周立功 USBCAN-2E-U** | USB | 2路 | 40K-1M | ¥500-800 | 周立功(ZLG)，工业级，文档全 |
| **PCAN-USB** | USB | 1路 | 40K-1M | ¥1500-2500 | Peak System，德国，行业标准，驱动完善 |

#### 软件适配工作

1. **新增ZlgCanAdapter / PCanAdapter**：继承CanAdapterBase，实现open/close/send/receive
2. **调用厂商DLL**：通过QLibrary动态加载厂商DLL，调用CAN_Open/CAN_Send/CAN_Receive
3. **波特率配置**：映射标准波特率(125K/250K/500K/1M)到厂商参数
4. **滤波配置**：调用厂商API设置硬件滤波
5. **测试验证**：用两个USB-CAN对发，验证收发正确性

#### 工作量
- 单适配器适配：4-8小时
- 双路同时收发测试：2小时
- 文档+示例：2小时

### 6.3 阶段2：专业CAN接口卡（专业级，高性能）

#### 推荐硬件

| 设备 | 接口 | 通道 | 特性 | 价格区间 |
|------|------|------|------|---------|
| **PCAN-PCIe** | PCIe | 2路 | 低延迟，高负载，车载测试标准 | ¥3000-5000 |
| **Vector VN1630** | USB/Ethernet | 2路CAN/CAN FD | 行业标杆，支持CAN FD/LIN，高性能 | ¥15000-30000 |
| **Kvaser PCIEcan 2.0** | PCIe | 2路 | 瑞典Kvaser，高时间精度，驱动完善 | ¥4000-6000 |
| **周立功 PCI-5010-U** | PCIe | 2路 | 国产PCIe，工业级 | ¥2000-4000 |

#### 软件适配工作

1. **时间戳精度提升**：专业卡硬件时间戳精度可达微秒级，修改CanFrame时间戳类型
2. **高负载优化**：接收线程使用环形缓冲区，避免丢帧；统计精度提升
3. **CAN FD支持**：如硬件支持CAN FD，扩展帧结构和数据长度(最大64字节)
4. **多通道管理**：支持多路CAN同时收发，通道独立配置/统计/显示
5. **触发功能**：利用硬件触发能力，实现复杂触发条件

#### 工作量
- 专业卡适配：8-16小时
- CAN FD扩展：8小时
- 多通道UI改造：8小时

### 6.4 阶段3：车载ECU实车测试（真实场景）

#### 测试对象

| 对象 | 说明 | 接入方式 |
|------|------|---------|
| **OBD-II接口** | 车辆诊断接口，16针，通常在驾驶位下方 | OBD转CAN线，接USB-CAN |
| **BCM(车身控制模块)** | 控制车窗/灯光/雨刷等 | CAN-H/CAN-L直接接入车身CAN总线 |
| **ECU(发动机控制单元)** | 动力总成CAN | 接入动力CAN总线（注意安全） |
| **BMS(电池管理系统)** | 新能源汽车电池管理 | 接入整车CAN总线 |
| **自定义开发板** | STM32+CAN收发器，模拟ECU | CAN-H/CAN-L直连 |

#### 实车测试注意事项

⚠️ **安全第一**：
1. **车辆熄火**：静态测试时车辆熄火，避免意外
2. **只收不发**：先只监听总线，确认报文格式后再尝试发送
3. **避免控制报文**：不要随意发送控制类报文（如刹车/油门/转向），可能导致车辆异常
4. **诊断接口优先**：通过OBD-II接口进行UDS诊断，不要直接接入动力CAN
5. **保险丝防护**：CAN总线接入建议加120Ω终端电阻和保险丝

#### 实车测试内容

1. **总线监听**：抓取车辆CAN报文，分析ID分布、周期、信号
2. **DBC逆向**：根据抓取的报文逆向分析信号定义，制作车辆DBC文件
3. **UDS诊断**：通过OBD接口读取车辆DID（VIN/故障码/数据流），清除故障码
4. **功能验证**：验证工具在真实总线负载下的稳定性、丢帧率、延迟

#### 推荐入门车辆

| 车型 | CAN总线 | OBD接口 | 难度 |
|------|---------|---------|------|
| 大众/奥迪 | 500Kbps，UDS标准 | 标准OBD | 中等，文档多 |
| 丰田/本田 | 500Kbps | 标准OBD | 简单，协议开放 |
| 国产新能源 | 250K/500K | 标准OBD | 中等，BMS数据丰富 |
| 自制STM32节点 | 自定义 | 无 | 最简单，完全可控 |

### 6.5 嵌入式移植方案（TC275/STM32）

#### 6.5.1 移植可行性分析

核心协议栈（CAN/DBC/ISO-TP/UDS）纯C++17实现，零Qt依赖，零平台依赖，可直接移植到嵌入式平台。业务层和GUI层需要替换为嵌入式实现。

```
PC端架构                          嵌入式架构
┌──────────────┐                ┌──────────────┐
│  GUI层(Qt)   │  → 替换为      │  LCD/串口输出 │
├──────────────┤                ├──────────────┤
│ 业务层(Qt)   │  → 替换为      │ FreeRTOS任务  │
├──────────────┤                ├──────────────┤
│ 核心协议栈    │  → 直接移植     │ 核心协议栈    │
│ (纯C++17)    │                │ (纯C++17)    │
├──────────────┤                ├──────────────┤
│ HAL层        │  → 替换为      │ 硬件CAN控制器 │
└──────────────┘                └──────────────┘
```

#### 6.5.2 方案A：英飞凌 TC275（汽车级）

| 项目 | 规格 |
|------|------|
| **核心** | TriCore 三核 200MHz |
| **存储** | 4MB Flash / 550KB RAM |
| **CAN** | 4路 MultiCAN+ (支持CAN FD) |
| **安全** | HSM硬件安全模块 |
| **认证** | AEC-Q100 / ISO 26262功能安全 |
| **应用** | 汽车ECU/网关/BMS/域控制器 |
| **开发环境** | HighTec / Tasking / AURIX Development Studio |
| **RTOS** | ERIKA Enterprise / FreeRTOS / AUTOSAR OS |

**移植工作内容：**
1. **核心协议栈移植**：C++17 → C语言（或保留C++，TC275支持C++），移除std::function（改用函数指针），移除std::deque（改用环形缓冲区）
2. **CAN驱动适配**：MultiCAN+硬件驱动，实现CanAdapterBase接口（或直接调用硬件API）
3. **ISO-TP/UDS运行环境**：用FreeRTOS任务替代Qt定时器，用队列替代信号槽
4. **安全访问**：利用HSM硬件加速密钥计算（AES-128）
5. **诊断响应**：TC275作为ECU响应诊断请求，或作为诊断仪发起请求

**工作量评估：** 核心协议栈移植40h + CAN驱动20h + 应用层开发40h = 约100h

#### 6.5.3 方案B：STM32F407（通用级）

| 项目 | 规格 |
|------|------|
| **核心** | Cortex-M4 168MHz (FPU) |
| **存储** | 1MB Flash / 192KB RAM |
| **CAN** | 2路 bxCAN (经典CAN 2.0B) |
| **安全** | 无HSM，软件加密 |
| **应用** | 工业控制/物联网/低成本诊断 |
| **开发环境** | Keil MDK / STM32CubeIDE / VS Code + OpenOCD |
| **RTOS** | FreeRTOS / RT-Thread / 裸机 |

**移植工作内容：**
1. **核心协议栈移植**：C++17 → C语言，STM32F407的RAM(192KB)足够运行协议栈
2. **CAN驱动适配**：bxCAN硬件驱动，HAL库或寄存器直接操作
3. **ISO-TP/UDS运行环境**：FreeRTOS任务+队列，或裸机定时器轮询
4. **上位机通信**：USB虚拟串口或以太网，将诊断数据上传到PC端工具
5. **安全访问**：软件实现AES-128密钥计算

**工作量评估：** 核心协议栈移植30h + CAN驱动15h + 应用层开发30h = 约75h

#### 6.5.4 两种方案对比

| 对比维度 | TC275 (汽车级) | STM32F407 (通用级) |
|---------|----------------|-------------------|
| **性能** | 三核200MHz，强 | 单核168MHz，够用 |
| **CAN通道** | 4路，支持CAN FD | 2路，仅经典CAN |
| **功能安全** | ISO 26262，HSM | 无 |
| **开发难度** | 高（工具链复杂） | 低（生态丰富） |
| **成本** | 高（¥150-300/片） | 低（¥20-50/片） |
| **适用场景** | 汽车前装/量产 | 学习/原型/后装 |
| **推荐优先级** | 长期目标 | 短期入门 |

#### 6.5.5 移植路线建议

```
阶段1：STM32F407裸机移植（入门）
  ↓ 验证协议栈在嵌入式环境的可行性
阶段2：STM32F407 + FreeRTOS（进阶）
  ↓ 多任务调度，实时性优化
阶段3：TC275 + FreeRTOS（汽车级）
  ↓ MultiCAN+驱动，HSM安全访问

```

### 6.6 硬件适配代码框架

新增硬件适配器只需继承CanAdapterBase，实现5个纯虚函数：

```cpp
class PCanAdapter : public CanAdapterBase {
public:
    bool open(const QString& interface, uint32_t bitrate) override;
    void close() override;
    bool sendFrame(const CanFrame& frame) override;
    bool receiveFrame(CanFrame& frame) override;  // 非阻塞
    void setFilter(const CanFilter& filter) override;
private:
    QLibrary m_pcanDll;  // 动态加载PCANBasic.dll
    TPCANHandle m_handle;
};
```

**硬件无关层不变**：核心协议栈、业务层、GUI层完全不需要修改，只需新增适配器类并在配置面板中添加选项。这就是面向抽象编程的优势。
